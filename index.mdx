Fireweave ([fireweave.ai](https://fireweave.ai)) is an AI release engineer that takes every coding-agent change to production safely with control points, cohort rollouts, guardrails, and live stability and adoption signals. These are the developer docs: SDKs for Node, Python, Go, Java, Rust, and the browser, plus onboarding for the CLI and coding-agent plugins.

Fireweave SDKs evaluate **control points** and optionally register **targets**. Your application authenticates with a Fireweave project key and talks to **fw-server**. The wire protocol and canonical envelopes still use the parameter name `flagKey`; the product name is control point.

v1 exposes exactly those two capabilities. The SDKs do not ship OpenFeature providers, and they do not expose `releases`, `exposures`, `signals`, or `capabilities`. Guardrails are evaluated by fw-server and the Fireweave console during rollouts; the SDK has no guardrails API.

If you are using a coding agent to integrate Fireweave, start with [For coding agents](/for-coding-agents).

## What you can do

- **Evaluate** boolean, string, number, and object decisions through nine methods. A read returns your default on failure and **does not throw**.
- **Register targets** once at login (`registerTarget` / language equivalent) so targeting rules can match durable properties.
- **Choose a mode** at init: `remote` (fw-server) or `local` (seeded in-process map). `mode` is required and never inferred.

<Note>
  The product noun is **control point**. `flagKey` remains the key name on the wire, in canonical envelopes, in conformance fixtures, and in `capabilities.features.flags`. The [onboarding guide](/onboarding) covers the product path — plugin skills and gradual rollouts — while these pages are the SDK reference.
</Note>
