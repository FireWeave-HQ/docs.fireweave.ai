title: "Exposures"
description: "An exposure is proof a target saw a control-point value. The SDK no longer exposes an exposures namespace."
---

An **exposure** records that a [target](/concepts/targeting) saw a [control-point](/concepts/control-points) value. fw-server still accepts capture batches on `POST /v1/capture` with `type: "exposure"`. That wire path is unchanged.

<Warning>
  The SDK `exposures` namespace (`record`, `flush`) and the per-call `sendExposure` opt-in were **removed from the v1 client surface** ([ADR-0010](https://github.com/FireWeave-HQ/fireweave-sdk/blob/master/docs/adr/0010-control-points-only-v1.md)). A v1 read is side-effect free: no read emits telemetry as a consequence of being called (`spec/control-points.md`). See [Migrate 2.1 to 2.3](/migration/v1).
</Warning>

## Why the concept still matters

Evaluation says what value was chosen. An exposure is the separate claim “we showed this variant.” Those are different facts. Keeping them separate is why a read must not imply assignment.

The console and analytics pipelines can still join on `targetingKey` + `flagKey`. That join is a platform concern. The SDK does not queue, dedup, or flush exposures for you.

This is **not** OpenFeature Tracking (spec §6). The bundled OpenFeature provider is gone; `track` was never implemented.

## How it relates

| Concept | Relation |
|---------|----------|
| [Control points](/concepts/control-points) | A v1 read does not emit an exposure |
| [Targeting](/concepts/targeting) | `targetingKey` is the join key when the platform records assignment |
| [Signals](/concepts/signals) | Different capture type (`type: "signal"`) |
| [Adapters](/concepts/adapters) | Remote adapters still speak `POST /v1/capture`. The client has no exposures API to drive it |

## What replaced the client API

Nothing on the client. If your 2.1 code called `exposures.record` / `flush`, or passed `sendExposure: true`, delete those calls. Do not expect `client.shutdown()` to drain an exposure queue you can no longer write to.

The test-server stub still implements `POST /v1/capture` because the wire path exists. That is not an SDK exposures API.
