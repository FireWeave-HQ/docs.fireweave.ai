---
title: "Signals and outcomes"
description: "Signals are release-safety telemetry. The SDK no longer exposes a signals namespace."
---

A **signal** is a telemetry envelope that says how a release is going. The spec still defines four kinds: `health`, `error`, `metric`, and `outcome`. Capture uses `type: "signal"` on `POST /v1/capture`.

<Warning>
  The SDK `signals` namespace (`recordHealth`, `recordError`, `recordMetric`, `recordOutcome`) was **removed in v1** ([ADR-0010](https://github.com/FireWeave-HQ/fireweave-sdk/blob/master/docs/adr/0010-control-points-only-v1.md)). `conformance/surface/control-points.surface.json` asserts the client must not expose `signals`. There is no replacement call on the client. See [Migrate 2.1 to 2.3](/migration/v1).
</Warning>

## Why the concept still matters

Evaluation says what value was chosen. Signals say what happened next — a component is degraded, an error you already classified, a numeric observation, or a user-visible result.

An **outcome** is a signal kind, not its own product object and not a separate docs page. Completing a [release](/concepts/releases) and recording an application outcome (checkout completed) are different platform facts. Neither is an SDK method in v1.

These are **not** the in-app Log / Alert / Block severities.

## How it relates

| Concept | Relation |
|---------|----------|
| [Releases](/concepts/releases) | Release lifecycle and outcome telemetry are both platform ideas now |
| [Exposures](/concepts/exposures) | Different capture type. Exposures prove assignment; signals report aftermath |
| [Errors](/production/errors) | The 15 `errorKind` values still describe evaluate failures. They are not a `recordError` API |
| [Adapters](/concepts/adapters) | Remote adapters still speak `POST /v1/capture`. The client has no signals API to drive it |

## What replaced the client API

Nothing on the client. If your 2.1 code called `signals.recordHealth` / `recordError` / `recordMetric` / `recordOutcome`, delete those calls.

Report health, errors, and outcomes through the observability tools you already run. Do not invent a Fireweave client helper to replace the cut namespace.
