title: "OpenFeature"
description: "v1 retired the bundled OpenFeature provider. Evaluate control points on the native controlPoints surface. An optional bridge package remains possible."
---

Fireweave v1 does **not** ship an OpenFeature provider.

[ADR-0010](https://github.com/FireWeave-HQ/fireweave-sdk/blob/master/docs/adr/0010-control-points-only-v1.md) (accepted 2026-08-20) retired `FireweaveProvider` and `FireweaveWebProvider` from every language SDK. There is no `makeFireweaveLocalProvider`, and no OpenFeature extra or peer dependency in the core packages.

<Warning>
  If you arrived here looking for a drop-in OpenFeature provider, that path is gone from the core SDK. Use the native [`controlPoints`](/concepts/control-points) surface, and follow [Migrate 2.1 to 2.3](/migration/v1).
</Warning>

## Why the provider was unbundled

ADR-0010's rationale, not a restatement of it:

- The provider was a thin delegation layer, not a second evaluation path. `getBooleanValue` and `resolveBooleanEvaluation` both called the same runtime.
- The OpenFeature peer dependency was mandatory by accident. A consumer who only called `controlPoints.*` was still told to install an OpenFeature SDK they never imported.
- The surface is seven languages. Requiring a mature OpenFeature SDK in each language made Rust and Swift depend on another project's coverage.

OpenFeature compatibility is **unbundled, not forbidden**. Nothing in ADR-0010 prevents a future optional bridge package that depends on both this SDK and an OpenFeature SDK. What is retired is the bridge shipping *inside* the core, where every consumer pays for it.

## What you call instead

v1 exposes exactly two capabilities: [control-point](/concepts/control-points) reads and [target registration](/concepts/targeting).

<CodeGroup>
```ts Node
import { initFireweave } from '@fireweaveai/server-sdk';

const fireweave = await initFireweave({
  mode: 'remote',
  apiUrl: process.env.FW_API_URL!,
  apiKey: process.env.FW_PROJECT_API_KEY!,
});

const enabled = await fireweave.controlPoints.getBooleanValue('new-checkout', false, {
  targetingKey: 'user_42',
});
```

```ts Web
import { initFireweave } from '@fireweaveai/web-sdk';

const fireweave = await initFireweave({
  mode: 'remote',
  apiKey: PUBLIC_FW_PROJECT_API_KEY,
  apiUrl: PUBLIC_FW_API_URL,
  context: { targetingKey: 'anonymous' },
});

// Synchronous — safe inside a render path.
const enabled = fireweave.controlPoints.getBooleanValue('new-checkout', false);
```
</CodeGroup>

The nine methods (`getBooleanValue`, `getStringValue`, `getNumberValue`, `getObjectValue`, the four `*Details` variants, and `evaluate`) live on `controlPoints` / `control_points` / `ControlPoints` in every language. See [Control points](/concepts/control-points).

`flagKey` is still the parameter name on the wire, on Decision envelopes, and in conformance fixtures. Removing the OpenFeature *dependency* did not rename `flagKey`. The product noun in prose is **control point**.

## What was removed

| 2.1 symbol | v1 status |
| --- | --- |
| `FireweaveProvider` | Removed from every language |
| `FireweaveWebProvider` | Removed |
| `makeFireweaveLocalProvider` / `getFwLocalCaptures` / `resetFwLocalCaptures` | Removed |
| OpenFeature peer / extra (`@openfeature/server-sdk`, `fireweave[openfeature]`, …) | Not required by the core SDK |
| Provider lifecycle (`setProviderAndWait`, `lazyReady`, domains) | Not an SDK concern |

A search for those symbols in a v1 install should find nothing. `conformance/surface/control-points.surface.json` asserts `mustNotExpose` for `FireweaveProvider` and `FireweaveWebProvider`.
